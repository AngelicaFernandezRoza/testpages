Task 3.1 / IaC

Infrastructure as Code (IaC)

Analogía maestra: Construir infraestructura sin IaC es como cocinar sin receta: cada vez que cocinas el plato queda diferente, no puedes darlo a otra persona para que lo cocine igual, y si te equivocas no puedes "deshacer". IaC es la receta en Git: reproducible, versionable, compartible y con historial de cambios.
☁️ AWS CloudFormation

Nativo de AWS. Define tu infraestructura en JSON o YAML. AWS gestiona el orden de creación, las dependencias y el rollback si algo falla.

# cloudformation-s3.yaml AWSTemplateFormatVersion: '2010-09-09' Description: Bucket S3 para la clase Resources: MiBucket: Type: AWS::S3::Bucket Properties: BucketName: mi-bucket-clase-2024 VersioningConfiguration: Status: Enabled Tags: - Key: Entorno Value: Clase # Desplegar con CLI: aws cloudformation deploy \ --template-file cloudformation-s3.yaml \ --stack-name mi-stack-clase
Free JSON/YAML Rollback automático Stacks
🌍 Terraform (HashiCorp)

Multi-cloud, open source. Lenguaje propio (HCL). Puede gestionar AWS, Azure, GCP y otros proveedores con el mismo código. El más usado en la industria.

# main.tf – Bucket S3 con Terraform provider "aws" { region = "eu-west-1" } resource "aws_s3_bucket" "clase" { bucket = "mi-bucket-terraform-clase" tags = { Entorno = "Clase" Gestionado = "Terraform" } } # Comandos: terraform init # Descarga providers terraform plan # Vista previa de cambios terraform apply # Aplica los cambios terraform destroy # Elimina todo
Multi-cloud HCL State file Plan/Apply
🐍 AWS CDK (Cloud Development Kit)

Define infraestructura con código real: Python, TypeScript, Java. Por debajo genera CloudFormation. Perfecto para developers que prefieren su lenguaje habitual.

# cdk_stack.py – Python from aws_cdk import aws_s3 as s3 class MiStack(Stack): def __init__(self, scope, id, **kwargs): super().__init__(scope, id, **kwargs) s3.Bucket(self, "MiBucket", versioned=True, removal_policy=RemovalPolicy.DESTROY )
Python/TS/Java Genera CFN Developer-friendly
🔧 Ansible (configuración de IaC)

Más orientado a configuración de sistemas que a provisión de infraestructura cloud. Sin agentes. YAML. Ideal para combinar con Terraform: Terraform crea la VM, Ansible la configura.

# playbook.yaml - name: Configurar servidor web hosts: all tasks: - name: Instalar nginx apt: name: nginx state: present - name: Copiar configuración template: src: nginx.conf.j2 dest: /etc/nginx/nginx.conf

Operaciones únicas vs. Procesos repetibles — Clave del examen

⚡ Operación ÚNICA (one-time)

Tareas que se hacen una sola vez, no se van a repetir, no necesitan ser reproducibles exactamente.

  • Explorar servicios nuevos
  • Crear recurso de prueba rápida
  • Consultar un log puntual
  • Cambio de emergencia en producción
→ Usa: Management Console o CLI puntual
🔄 Proceso REPETIBLE (repeatable)

Tareas que se harán varias veces, en varios entornos (dev/staging/prod), o que deben ser reproducibles exactamente por cualquier miembro del equipo.

  • Crear entorno completo de la app
  • Deploy de producción
  • Replicar infra en otra región
  • Onboarding de nuevo cliente
→ Usa: IaC (CloudFormation, Terraform, CDK)

🎯 Lo que pregunta el examen sobre IaC

  • AWS CloudFormation es el servicio nativo de IaC en AWS → respuesta cuando digan "nativo AWS"
  • IaC permite consistencia entre entornos y reduce errores humanos
  • Cuando pregunten "¿cómo hacer reproducible el aprovisionamiento?" → IaC
  • CloudFormation usa el concepto de Stack (conjunto de recursos gestionados juntos)
  • Si un Stack falla durante el despliegue → rollback automático
Task 3.1 / Modelos de Despliegue

Modelos de despliegue en la nube

⚠️ CONFUSIÓN MÁS FRECUENTE EN EL EXAMEN

Hybrid Cloud ≠ Hybrid Environment

Hybrid Cloud: Combina nube pública + nube privada (ambas cumplen criterios de cloud computing: auto-servicio, elasticidad, etc.)

Hybrid Environment: Tu data center on-premises + AWS juntos. El data center tradicional NO es cloud.

Ejemplo del examen:

"Una empresa usa AWS y su data center local conectados mediante Direct Connect" →

✓ Esto es un HYBRID ENVIRONMENT, no hybrid cloud

☁️
Public Cloud (Nube Pública)
AWS, Azure, Google Cloud — el foco principal del examen CLF-C02

Infraestructura gestionada por un tercero (AWS). Accesible públicamente. Multi-tenant. Pago por uso. Cumple los 5 criterios NIST de cloud computing.

  • Todo en AWS es public cloud por defecto
  • Escala ilimitada bajo demanda
  • Sin inversión inicial (CAPEX ≈ 0)
  • AWS gestiona el hardware
☁️ Analogía: Vivir en apartamento alquilado. No compras el edificio, pero tienes tu piso, llave propia y puedes cambiarte cuando quieras.
Ejemplo AWS: EC2, S3, RDS, Lambda…
Multi-tenant OPEX Elástico
🔒
Private Cloud (Nube Privada)
Dedicada a una sola organización · Cumple criterios cloud · Servicio dedicado

Infraestructura cloud dedicada exclusivamente a tu organización. Puede estar en tus instalaciones o en las del proveedor. La diferencia con on-premise: cumple criterios cloud (auto-servicio, elasticidad, metering).

  • AWS Outposts: rack de AWS en tu data center
  • Single-tenant
  • Control total del entorno
  • Cumplimiento normativo estricto
🏠 Analogía: Casa propia o chalet privado. Tú decides todo, pero tienes que mantenerlo.
Ejemplo AWS: AWS Outposts (hardware AWS en tu CPD)
Single-tenant CAPEX alto Control total
🔄
Hybrid Cloud (Nube Híbrida)
Public + Private Cloud · Ambas deben cumplir criterios cloud

Combinación de nube pública y privada que trabajan juntas. Permite mover cargas entre ambas entornos de forma fluida.

  • Datos sensibles en private cloud
  • Burst to public cloud en picos
  • Transición gradual a la nube
⚡ AWS Outposts es la solución híbrida nativa de AWS: extiende AWS a tu data center.
🏘️ Analogía: Casa propia + apartamento alquilado extra cuando tienes visitas de temporada.
Hybrid Cloud ≠ Hybrid Environment
Si usas tu data center + AWS = Hybrid Environment
Si usas AWS Outposts + AWS = Hybrid Cloud
🌍
Multi-cloud
2 o más proveedores de nube pública · AWS + Azure + GCP

Uso simultáneo de múltiples proveedores de nube pública para distintas cargas de trabajo.

  • Evita dependencia de un solo proveedor (vendor lock-in)
  • Mejor servicio de cada cloud
  • Redundancia entre proveedores
  • Alta complejidad operativa
🏢🏢🏢 Analogía: Apartamentos en varios edificios de distintos propietarios. Más libertad, más llaves que gestionar.
No vendor lock-in Alta complejidad IaC esencial
🖥️
On-Premises (On-Prem)
Tu data center físico · NO es cloud · Solo sirve para contrastar con cloud en el examen

Infraestructura física en tus instalaciones. No cumple los criterios de cloud computing (no es elástica, no tiene auto-servicio instantáneo). Se menciona en el examen únicamente para contrastar.

  • Compras el hardware
  • Tú lo mantienes todo
  • Escalado muy lento (semanas/meses)
  • CAPEX brutal
Para el examen: On-premise aparece siempre como el "pasado" del que AWS te ayuda a migrar, o como parte de un hybrid environment.
Task 3.1 / Servicios AWS: Public vs Private

Zonas de red en AWS: Público vs Privado

⚡ Concepto clave: En AWS, "público" y "privado" describen la conectividad de red de un servicio, NO quién puede usarlo o si necesita credenciales. Un servicio "público" de AWS simplemente tiene una interfaz de red conectada al internet público.

Arquitectura de zonas de red en AWS

INTERNET PÚBLICO

Cualquier usuario con conexión a internet

AWS PUBLIC ZONE

Servicios con interfaz de red conectada al internet público. Accesibles desde internet CON las credenciales correctas.

☁️ Amazon S3 🔑 IAM ☁️ CloudFront 📊 CloudWatch 🔧 AWS CLI endpoint 🌐 EC2 Public IP

💡 "Público" = accesible vía internet. Requiere autenticación pero no VPN.

AWS PRIVATE ZONE (VPC)

Completamente aislado. Sin acceso directo desde internet. Solo accesible desde dentro de la VPC (o mediante configuración explícita).

🖥️ EC2 (private subnet) 🗄️ RDS (private) 🏗️ VPC Internals 📁 EFS (privado)

🔒 "Privado" = aislado de internet. Para acceder, necesitas configuración explícita (IGW, NAT, VPN…)

Gateways: ¿cuándo usar cuál?

🚪 Internet Gateway (IGW)

Permite que instancias EC2 en una subred pública envíen y reciban tráfico desde internet. Horizontalmente escalado y altamente disponible.

Analogía: La puerta principal del edificio. Permite entrada y salida al exterior.
  • Para instancias con IP pública
  • Tráfico bidireccional (entrada + salida)
  • Necesita ruta en la tabla de rutas
EC2 pública → IGW → Internet ✓
Internet → IGW → EC2 pública ✓
🔀 NAT Gateway

Permite que instancias en subredes privadas salgan a internet (actualizaciones, descargas) sin ser accesibles desde internet.

Analogía: El portero del edificio. Deja salir a los residentes privados pero no deja entrar a desconocidos.
  • Para instancias en subred privada
  • Solo tráfico de salida
  • Vive en subred pública, usa IGW
  • Gestionado por AWS (HA automática)
EC2 privada → NAT GW → IGW → Internet ✓
Internet → NAT GW → EC2 privada ✗
🔗 Egress-Only Internet Gateway (IPv6)

Equivalente al NAT Gateway pero para tráfico IPv6. Permite salida a internet desde instancias IPv6 privadas, bloqueando las conexiones entrantes. Con IPv6 no existe el concepto de "IP privada" como en IPv4 — todas las IPs IPv6 son globalmente únicas, por eso se necesita este gateway.

🎯 Pregunta trampa clásica del examen

  • P: "¿Qué necesita una instancia EC2 en subred pública para conectarse a internet?"
  • R correcta: Internet Gateway (+ IP pública + ruta en tabla de rutas)
  • P: "¿Qué necesita una instancia privada para actualizar paquetes sin ser accesible desde internet?"
  • R correcta: NAT Gateway (en subred pública) + ruta en tabla de rutas de la subred privada
Task 3.1 / Opciones de Conectividad

Conectividad de red con AWS

Tres formas principales de conectar tu red local (o usuarios) con los servicios de AWS. Cada una tiene casos de uso, ventajas y limitaciones distintas.

🌐 Internet Público

Siempre disponible Menor costo Menor seguridad

Acceso a servicios AWS a través de la red pública de internet. Los servicios públicos de AWS (S3, APIs, etc.) son accesibles directamente.

✓ CUÁNDO USAR
  • Acceso desde cualquier lugar
  • Servicios AWS públicos (S3, APIs)
  • Aplicaciones públicas
  • Sin inversión adicional
✗ LIMITACIONES
  • Tráfico no cifrado sin HTTPS
  • Latencia variable
  • Riesgo de seguridad
  • Sin SLA de red
Usuario → Internet Público → AWS ━━━━━━━━━━━━━━━━━━━━━━━━ 👤 Usuario en casa ↓ HTTPS 🌐 Internet ↓ 📦 S3, CloudFront, API Gateway (Servicios en AWS Public Zone)

🔐 AWS VPN (Virtual Private Network)

Cifrado Rápido de implementar Internet subyacente

Túnel cifrado sobre internet que conecta tu red local con tu VPC en AWS. Existen dos tipos:

  • Site-to-Site VPN: Conecta tu CPD/oficina con AWS VPC. Requiere un Customer Gateway (router físico).
  • Client VPN: Conecta dispositivos individuales (portátiles, móviles) con AWS VPC. Para empleados remotos.
✓ VENTAJAS
  • Cifrado automático (IPsec)
  • Fácil de configurar
  • Costo bajo
  • Disponible en minutos
✗ LIMITACIONES
  • Depende de internet
  • Latencia variable
  • Ancho de banda limitado
  • Sin SLA garantizado
Site-to-Site VPN ━━━━━━━━━━━━━━━━━━━━━━━━ 🏢 Tu data center [Customer Gateway] ↓ Túnel IPsec cifrado ↓ (sobre internet) ↓ [Virtual Private Gateway] VPC en AWS (zona privada) └─ EC2, RDS, etc. Client VPN ━━━━━━━━━━━━━━━━━━━━━━━━ 💻 Portátil del empleado ↓ TLS cifrado ↓ (internet) ↓ VPC en AWS

⚡ AWS Direct Connect (DX)

Conexión dedicada Alta velocidad Baja latencia Alto costo Meses para provisionar

Conexión física privada dedicada entre tu red y AWS. No usa internet público. Velocidades de 1 Gbps a 100 Gbps.

Analogía: Tener una autopista privada directa a AWS en lugar de usar la carretera pública (internet). Más cara, pero sin atascos ni semáforos.
✓ VENTAJAS
  • Latencia predecible
  • Ancho de banda alto
  • Sin internet (+ seguro)
  • Reducción coste datos
✗ LIMITACIONES
  • Caro (hardware + operador)
  • Tarda semanas/meses
  • Sin cifrado nativo
  • Un punto de fallo físico
Direct Connect ━━━━━━━━━━━━━━━━━━━━━━━━ 🏢 Tu data center ↓ Fibra dedicada ↓ (SIN internet) [AWS Direct Connect Location] ↓ (AWS backbone privado) ↓ VPC / Servicios AWS ⚡ Keyword clave del examen: "dedicated connection" = Direct Connect Velocidades disponibles: 1 Gbps | 10 Gbps | 100 Gbps

CLF-C02 / Preparación Examen

🎯 Preguntas tipo examen

Haz clic en cada pregunta para ver la respuesta y la explicación.

Una empresa quiere crear un entorno de pruebas idéntico al de producción cada vez que el equipo de QA lo necesite. ¿Cuál es la solución más adecuada?

✅ Usar Infrastructure as Code (IaC) con AWS CloudFormation

El escenario pide un proceso repetible y consistente. La Management Console no garantiza reproducibilidad. La CLI podría funcionar pero sin gestión de dependencias ni rollback. CloudFormation permite definir el entorno completo como código, desplegarlo en minutos y destruirlo cuando no se necesite, ahorrando costos.

¿Cuál de los siguientes describe mejor la diferencia entre AWS Site-to-Site VPN y AWS Direct Connect?

✅ Site-to-Site VPN usa internet cifrado; Direct Connect usa una conexión privada dedicada sin internet

La palabra clave de Direct Connect en el examen es "dedicated connection" (conexión dedicada). VPN siempre pasa por internet, aunque esté cifrado. DX nunca usa internet público.

Una empresa usa AWS junto con su data center local conectados mediante Direct Connect. ¿Cómo se clasifica este entorno?

✅ Hybrid Environment (entorno híbrido), NO Hybrid Cloud

El data center local NO es cloud (no cumple los criterios de cloud computing). Por tanto, AWS + data center = hybrid environment. Hybrid Cloud requeriría que el data center local fuera una nube privada (como AWS Outposts) que cumpliera criterios cloud.

¿Qué tipo de gateway necesita una instancia EC2 en una subred privada para descargar actualizaciones de software desde internet SIN ser accesible desde internet?

✅ NAT Gateway (ubicado en una subred pública)

El NAT Gateway permite tráfico de salida (outbound) desde subredes privadas hacia internet, pero bloquea las conexiones entrantes (inbound). Él mismo vive en una subred pública y usa el Internet Gateway. No se necesita Internet Gateway directamente en la subred privada.

Un desarrollador quiere integrar operaciones de Amazon S3 directamente en su aplicación Python. ¿Cuál es la mejor opción?

✅ AWS SDK para Python (Boto3)

Los SDKs son la opción correcta cuando se quiere integrar AWS en una aplicación. La CLI sirve para scripts de terminal, no para integrar en código de aplicación. La Management Console es gráfica. Boto3 abstrae la complejidad de las APIs directas y gestiona la autenticación automáticamente.

¿Cuál es la definición correcta de un servicio "público" de AWS según la arquitectura de red de AWS?

✅ Un servicio que puede ser accedido desde cualquier lugar con conexión a internet (como Amazon S3)

"Público" en AWS se refiere a la conectividad de red, no a si el servicio requiere credenciales. Amazon S3 es un servicio público: se accede por internet, pero requiere autenticación. Amazon EC2 en una subred privada es un servicio privado: sin acceso directo desde internet.

Una empresa necesita migrar 50TB de datos a AWS regularmente con bajo costo de transferencia y alta velocidad. ¿Qué opción de conectividad es la más adecuada?

✅ AWS Direct Connect

Para grandes volúmenes de datos con necesidad de alta velocidad y bajo costo por GB, Direct Connect es superior. También ofrece latencia predecible. Si el volumen fuera masivo y puntual (petabytes), podría considerarse AWS Snowball, pero para transferencias regulares, DX es la solución.

¿Cuál de estos NO es un método de acceso a servicios AWS?

✅ La respuesta depende de las opciones del examen, pero típicamente incluirán "FTP" o "SFTP" o "Telnet" como distractor incorrecto

Los métodos de acceso a AWS son: API REST, SDK, CLI y Management Console. Todo lo demás (FTP, Telnet, SFTP) no son métodos de acceso a los servicios AWS en sí.

📝 Conceptos clave a memorizar para el examen

  • CloudFormation = IaC nativo de AWS
  • SDK = integrar AWS en tu aplicación
  • CLI = automatizar con scripts, operaciones en terminal
  • Console = exploración, operaciones únicas, visualización
  • Direct Connect = "dedicated connection" = no usa internet
  • VPN = cifrado, sí usa internet
  • Internet Gateway = tráfico bidireccional para subredes públicas
  • NAT Gateway = solo salida, para subredes privadas
  • Hybrid Cloud ≠ Hybrid Environment (confusión frecuente)
  • AWS Outposts = hardware AWS en tu CPD = private cloud / hybrid cloud

🔧 TALLER 1 — Los 4 métodos de acceso a S3 (1 tarea, 4 herramientas)

Objetivo: Crear un bucket S3 y subir un archivo con los 4 métodos distintos. Contrastar la experiencia.

  1. Management Console: Accede a console.aws.amazon.com → S3 → "Create bucket". Nombre: mi-bucket-consola-[tunombre]. Sube un archivo con drag&drop.
  2. CLI: Configura credenciales con aws configure. Ejecuta aws s3 mb s3://mi-bucket-cli-[tunombre] --region eu-west-1. Sube con aws s3 cp archivo.txt s3://mi-bucket-cli-[tunombre]/
  3. SDK Python (Boto3): Instala con pip install boto3. Escribe un script Python que cree un bucket y suba un objeto. Ejecuta el script.
  4. CloudFormation (IaC): Crea un template YAML con un recurso AWS::S3::Bucket. Despliégalo con aws cloudformation deploy --template-file s3.yaml --stack-name mi-stack

🗣 Reflexión para clase: "¿Cuál fue más rápido? ¿Cuál escalaría mejor a 100 buckets? ¿Cuál deja trazabilidad?"

🔧 TALLER 2 — VPC: Subredes públicas y privadas con gateways

Objetivo: Crear una VPC con subredes pública y privada. Verificar la diferencia de conectividad.

  1. Crear VPC con CIDR 10.0.0.0/16 en la consola
  2. Crear subred pública: 10.0.1.0/24 y subred privada: 10.0.2.0/24
  3. Crear y adjuntar un Internet Gateway a la VPC
  4. Modificar la tabla de rutas de la subred pública: añadir ruta 0.0.0.0/0 → IGW
  5. Crear un NAT Gateway en la subred pública (con Elastic IP)
  6. Modificar la tabla de rutas de la subred privada: añadir ruta 0.0.0.0/0 → NAT GW
  7. Lanzar EC2 en subred pública (con IP pública) y otra en subred privada
  8. Verificar: EC2 pública puede hacer ping a internet. EC2 privada puede hacer curl google.com pero no es accesible desde internet.

🔗 Conecta con IaC: Tras hacerlo manual, mostrar el CloudFormation equivalente. "Esto nos ha llevado 30 minutos manualmente. El template tarda 3 minutos."

🔧 TALLER 3 — Mi primera infraestructura con Terraform (IaC)

Objetivo: Provisionar infraestructura básica (VPC + subred + EC2) con Terraform. Experimentar el ciclo plan/apply/destroy.

  1. Instalar Terraform: sudo apt install terraform o descarga desde terraform.io
  2. Configurar credenciales AWS: aws configure o variables de entorno
  3. Crear directorio del proyecto y archivo main.tf con provider AWS y recurso VPC
  4. Ejecutar terraform init → descarga el provider de AWS
  5. Ejecutar terraform plan → ver qué va a crear (sin tocar nada aún)
  6. Ejecutar terraform apply → confirmar con yes → infra creada
  7. Modificar el CIDR de la subred en el .tf → terraform plan → ver el diff
  8. Ejecutar terraform destroy → limpiar todo. Contrastar con borrado manual.

💡 Debate: "¿Por qué Terraform tiene un plan antes del apply? ¿Qué analogía tiene con git diff?"

💬 Actividad de debate — Elige el modelo

Presenta a tus alumnos estos 3 escenarios. Cada grupo debe elegir el modelo de despliegue y método de acceso más adecuado y justificarlo:

  1. Startup de comercio electrónico con 5 desarrolladores que necesita escalar rápido, sin capital inicial y con tráfico impredecible. ¿Qué modelo de nube? ¿CLI, console o IaC?
  2. Hospital público con datos clínicos que deben cumplir regulaciones de la UE, no pueden salir del territorio nacional, y tienen un equipo IT de 50 personas. ¿Qué modelo? ¿Qué conectividad con AWS?
  3. Banco que usa un mainframe on-premises legacy y quiere modernizar gradualmente, añadiendo nuevos servicios en AWS sin migrar el mainframe. ¿Hybrid cloud o hybrid environment? ¿VPN o Direct Connect?
